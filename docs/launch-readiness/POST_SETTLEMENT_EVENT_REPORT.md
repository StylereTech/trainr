## Change

The webhook now resolves these platform-account events through current provider relationships, not event amounts or transfer metadata: `transfer.created`, `transfer.updated`, `transfer.reversed`, `application_fee.created`, `application_fee.refunded`, `application_fee.refund.updated`, `charge.updated`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`, `charge.dispute.funds_withdrawn`, and `charge.dispute.funds_reinstated`.

Transfer source charge, application-fee originating charge and charge-to-payment identity are re-read. Ambiguous local mappings fail closed. The shared verifier rechecks the triggering object against the captured charge under the booking/payment locks. Unrelated platform charges, unlinked available-balance transfers and direct-charge application fees are ignored; connected-account copies are ignored before any provider read. A TRAINR-tagged but unlinked charge remains a reconciliation conflict.

Every settlement check now reads current charge-filtered dispute history, including inquiries before `charge.disputed` becomes true. Identity, currency, mode, amounts, statuses, duplicate IDs and balance-transaction arithmetic are validated. History is bounded to one complete page of 100; incomplete/excessive history requires review. A triggering dispute must exist in that history. Dispute reads join the existing four-second/no-SDK-retry policy and 25-second SQL transaction bound.

Review observations contain only financial IDs, refund/reversal totals, dispute statuses/deadlines and balance-transaction amounts. Raw evidence, card details and customer communications are not copied. A stable hash of sorted, sanitized observations deduplicates replay while allowing a changed amount/status/funds observation to generate a new notice. Both parties and current active admins receive notices atomically. A failure to insert any notice rolls financial writes back for retry. Existing user notification retention rules still apply; these notices are operational records, not a new immutable accounting ledger.

Review additionally found a recipient authorization race in the new fanout. Admin selection now uses an ordered `FOR SHARE` query after provider reads and holds those user locks through notification commit. A role/deactivation update that commits first is re-evaluated before selection; a later update cannot interleave between selection and delivery. No admin user lock is held across external Stripe reads in this transaction. This hardening applies to this settlement-review fanout; it does not claim every legacy notification producer has been audited.

**Alert-delivery gap:** repository inspection found `GET/PATCH /api/notifications` but no notification inbox or frontend consumer. All notification claims in this report mean persisted, recipient-scoped records, not email delivery, visible browser alerts or proof that a person received them. A usable inbox/review surface and end-to-end delivery tests remain a fixable launch item. Stripe Dashboard monitoring is still required for dispute deadlines until that work is complete.

Fully refunded payments can now receive lifecycle review without a late success overwriting their refund status. Inquiries, closed/won disputes and reversals do not automatically reopen or confirm a held booking. Existing confirmed/terminal history is preserved. There is no refund, reversal, transfer, evidence submission, dispute acceptance or payout execution in these handlers.

3. Treat 409 as an identity/model/history reconciliation case, not a successful payment receipt.
