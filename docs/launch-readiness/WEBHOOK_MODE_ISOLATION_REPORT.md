## Finding And Fix

**P1 isolation gap:** signature verification did not compare the signed event's `livemode` with the runtime Stripe secret-key mode. Opposite-mode events reached booking payment, refund, financial reconciliation, package payment and Connect-readiness handlers. Downstream receipt/identity checks remain important and may reject individual events; this finding does not prove a real cross-environment charge, database mutation or loss of funds.

Stripe documents that a Connect endpoint can receive live and test events and recommends inspecting their mode: [Connect webhook configurations](https://support.stripe.com/questions/connect-account-webhook-configurations?locale=en-GB). Mode filtering must therefore follow authentication, not replace it.

`verifyWebhookSignature` now verifies the platform or separate Connect signature and existing Connect scope checks first. It requires boolean `livemode` and a recognized standard/restricted test/live key prefix. A valid opposite-mode event returns a deliberately nullable result; the route acknowledges it as `{ received: true, ignored: 'event_mode_mismatch' }` before any handler. Matching-mode events retain the existing path. Malformed mode, unknown key format, tampering, invalid signatures and invalid Connect scope fail closed with the existing 400 response. No timeout, signature replay tolerance or payment assertion was weakened.

This does not prove that a deployment has the correct credentials, Stripe account, database or publishable key. It cannot distinguish two separate sandboxes that both use test mode. Provider configuration and actual hosted receipt verification remain separate gates. Acknowledging an opposite-mode event intentionally prevents it from changing this environment; operators must still configure the appropriate destination for events that should be processed elsewhere. If an event was ignored because the runtime was misconfigured, correcting credentials does not replay that acknowledged event: an authorized operator must verify the account/mode/destination and resend the original event through Stripe, then verify persistence. No such provider action was performed in this pass.
