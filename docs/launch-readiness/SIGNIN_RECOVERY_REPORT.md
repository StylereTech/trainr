## Reproduction

1. Invoke the actual sign-in form's submit handler with a successful synthetic credentials response.
2. Return an empty/null session, a missing/invalid user ID, an unknown role, or an HTTP 503 session response.
3. Observe router calls. Expected: remain on sign-in, show a persistent error, and permit retry. Actual baseline: navigation to `/parent/dashboard`, including when no authenticated user exists.
4. Return undefined/unsuccessful credentials results. Expected: no session request or navigation. Baseline incorrectly continued for results without an explicit error.
5. Exercise valid parent, trainer and admin sessions as positive controls.

Baseline unit result: **13 failed / 3 passed**, 16 cases, exit 1. Six invalid-session cases and the HTTP failure demonstrated erroneous parent navigation. Other failures cover unsuccessful result handling and lack of persistent form-error state. This establishes a client recovery/UX bug, not an authorization bypass: server guards remain unchanged.

## Fix

- Require a successful credentials result before requesting a session.
- Require a nonempty string user ID and an explicit supported role before navigation; remove the implicit parent fallback.
- Fetch session state without browser caching.
- Keep a generic, accessible inline error visible on the form; clear it on retry and restore the submit button after failure.
- Add standard username/current-password autocomplete metadata. No credential values are stored by this change.
