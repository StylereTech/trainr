## Changes And Policy

- PostgreSQL `rate_limit_buckets` holds a sliding window of accepted timestamps, serialized by a row-locking upsert inside a transaction. A database-clock read follows lock acquisition. Independent processes/clients with the same key and secret share the same budget; no in-memory fallback exists.
- Keys are HMAC-SHA256 digests of versioned context, policy and logical identity, using server-only `NEXTAUTH_SECRET`. No raw IP/email is persisted in this table. Consistent strong keys across instances are mandatory; rotation resets these budgets as well as affecting sessions/account-link behavior.
- Blocked requests do not append timestamps or extend the window. Each bucket expires after its newest accepted hit plus its own policy window. A separate bounded delete removes up to 100 expired buckets per call, using an indexed expiry scan and `SKIP LOCKED`. Idle deployments retain expired rows until another call or reviewed scheduled pruning; no background cleanup job was provisioned here.
- Consumption uses a two-second transaction acquisition limit and five-second transaction timeout. Missing configuration or database failures deny the operation. Auth APIs return controlled 503 responses on limiter failure; credential login returns a generic denial without credential lookup. Forgot-password budget exhaustion keeps its existing generic 200 response to avoid exposing account existence.
- Current limits: registration 5/minute/IP; verification redemption 10/minute/IP; reset redemption 5/15 minutes/IP; forgot-password 3/15 minutes/IP; authenticated verification resend 3/15 minutes/user. New credential login budgets: 30/15 minutes/IP plus 10/15 minutes/normalized email, including successful attempts. Legitimate users sharing an address may hit limits; account-targeted throttling also creates a temporary lockout tradeoff requiring monitoring.
- `getClientIp` reads only `x-vercel-forwarded-for` when runtime `VERCEL=1`. Otherwise, absent/invalid/ambiguous input uses the shared `unknown` bucket, never a caller-controlled fallback. IPv6 is canonicalized; zone identifiers are rejected. Different IPv6 addresses/subnets are not aggregated in this pass, and botnets/volumetric protection still require edge controls.
- [Vercel's header documentation](https://vercel.com/docs/headers/request-headers) describes its platform IP headers and proxy behavior. Real ingress/header rewriting must still be verified in staging. Non-Vercel deployment needs an explicitly reviewed trusted-proxy adapter; setting `VERCEL=1` on an exposed non-Vercel server would create a spoofing risk and is not an approved production setup.
- The installed NextAuth credentials provider supplies request headers to `authorize`; login now consumes both budgets before database credential lookup or bcrypt. Oversized email/password inputs are rejected before that work. The UI uses a generic credentials-or-retry message, not a claim that every denial means a wrong password.
