## Deployment Procedure

**New empty staging database only:** configure an isolated database and credentials first, verify the target identity, then run the repository's installed Prisma `migrate deploy` against `prisma/schema.prisma`. Confirm all 11 migrations and schema parity before starting the app. Do not use `db push` as a substitute for the ordered SQL: it omits the partial index and SQL CHECK safeguards. Do not run the demo seed against production.

**Existing database: no automatic production command is authorized by this report.** Obtain a tested backup/restore plan and inspect the actual schema, records, `_prisma_migrations`, applied checksums and SQL-only constraints on a protected clone. Determine whether the original schema already exists in full and which later changes are actually present. Merely observing the live commit or a healthy connection is insufficient.

Only after independently verifying the original baseline objects may an operator use `prisma migrate resolve --applied 0_baseline` to record that already-existing schema. That command records history; it does not validate or repair the database. Never mark an absent later migration applied to bypass an error. Existing partial/failed migrations, missing original objects, prior `db push`, modified checksums, manually added columns and other drift need their own reviewed reconciliation plan. A phone-only ledger and an untracked pre-phone schema are the two synthetic scenarios covered here, not an exhaustive survey of production states.

Coordinate application rollout with the pending session-version/deactivation, checkout-attempt, refund, Connect-attempt, retry-identity, token and rate-limit changes. Old bearer-token invalidation is intentional and affects outstanding links. Preserve financial/provider history and investigate unsupported legacy attempts; do not fabricate receipts or turn old wallet credits into an additional withdrawable balance. Rehearse on the clone, verify restored backups, apply approved migrations in the agreed window, deploy the exact audited source, and test the real staging and production flows. Rollback must account for data/schema compatibility; an old app deployment alone is not a database rollback.

Reference: Prisma's [v6 existing-project migration guidance](https://www.prisma.io/docs/orm/v6/prisma-migrate/getting-started) describes generating and recording a baseline for already-existing objects. The repository-specific validation and restrictions above are based on this rehearsal, not proof of the production database's state.
