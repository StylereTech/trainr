## Fix and retest status

The audit-branch `src/app/admin/payouts/page.tsx` already uses a nullable `summary`, validates the response shape and renders a retryable error state. Its `GET /api/admin/payouts?view=payments` contract has separate tests. This corrected source is **not** what `trainr.cc` serves; no public redeploy or authenticated public retest was performed. Verify the target project's environment/schema, promote only the reviewed release, then repeat the admin click and inspect actual API response before resolving this defect. The public site's old refund-policy promises and the restricted Stripe Connect state remain separate launch blockers.

**Decision:** production money-flow signoff **HOLD**. These tests prove login and booking selection, not a sandbox paid booking, signed webhook, transfer, refund or bank payout.

## Automated regression, 2026-10-17 20:58 UTC

The former `e2e/admin-flow.spec.ts` payout checks only asserted that the URL contained `/admin/payouts` and the API was not 404; neither could catch this crash or the incompatible response contract. The audit branch now requires a visible **Recorded Payments** heading and a 200 `view=payments` response containing a payment array, four numeric summary fields and pagination.

Focused command against `trainr.cc`: `npm run test:e2e -- e2e/admin-flow.spec.ts --grep "payouts page loads|payouts API returns data" --project=chromium --workers=1`. **0/2 passed as expected on old Production**: the heading was absent because the page showed the client-side exception (Playwright screenshot `test-results/admin-flow-Admin-Flow-Payouts-payouts-page-loads-chromium/test-failed-1.png`), and the legacy API returned 200 without `payments`. The first attempt never started tests because Playwright's matching Chromium executable was absent; after installing Chromium, both assertions ran and failed on application behavior. This is a reproduced release-gate failure, **not** a green retest or proof that the audit branch has been promoted. The corrected app/API contract must be exercised again after controlled deployment.

## Public trainer Connect status, 2026-10-17 21:03 UTC

The opt-in read-only `e2e/production-trainer-connect-status.spec.ts` signed in as the supplied trainer demo and called `GET /api/trainer/stripe-connect`; it did **not** POST or open onboarding. Run with `TRAINR_PUBLIC_DEMO_STATUS=1`, the focused Playwright case reached the endpoint and failed on its provider-error assertion. Actual: HTTP **200**, `stripeConfigured: true`, `hasAccount: true`, `error: "Could not verify account"`. The same result repeated on a second run. Other readiness flags were absent from the old response, so the linked account's current charges/transfers/payouts state is **not** inferred from this call. This is a production provider/API verification failure, not just a trainer who has not begun setup.
