## Findings And Fixes

- P1: retrying an ambiguously committed creation could duplicate a child. A parent-scoped request UUID ledger now commits with profile creation, hashes the normalized request, returns the current saved profile on an exact replay and rejects changed payloads. Deleting an unbooked athlete leaves a null-reference tombstone so a delayed replay cannot resurrect it.
- P1: the initial new parent lock created a PostgreSQL deadlock against booking's parent foreign-key check. Changed only the parent serialization lock to `FOR NO KEY UPDATE`; the athlete retains `FOR UPDATE`. [PostgreSQL lock compatibility](https://www.postgresql.org/docs/17/explicit-locking.html) explains why this permits KEY SHARE while serializing parent mutations. Strict real SQL races confirm one successful operation, an expected domain conflict for the other, and no orphan.
- P2: invalid/rolled/future birth dates, overlong fields, unknown/inactive sports, mixed valid/invalid lists and canonical id/slug duplicates were accepted or silently dropped. Shared validation and transactionally locked active catalog resolution now reject the whole invalid request.
- P2: no parent profile edit/delete workflow existed. Added owned PATCH/DELETE endpoints and dashboard edit links with exact revision checks. Concurrent edits cannot silently overwrite each other. Unbooked profiles can be deleted after confirmation; any booking history prevents physical deletion and requires support review.
- P2: athlete reads lacked an explicit parent role boundary. GET/POST/PATCH/DELETE now require a current active parent and select explicit response fields; foreign profiles return 404 for mutations. Request hashes, account fields and parent IDs are not returned.
- P2: standalone and inline forms had diverging hard-coded sports. Both use the shared editor and active database catalog. Errors are not represented as empty data. The inline close control is disabled while a write is pending or uncertain.
- Creation retry identity persists only while the form stays mounted. Refresh, navigation or closing the browser does not preserve an unsaved draft/request. After those events, inspect the dashboard before creating again; cross-navigation recovery is an open product limitation.
